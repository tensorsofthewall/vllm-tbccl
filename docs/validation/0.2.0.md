## Pairings validated

| Pairing | vLLM | Model | Link |
|---|---|---|---|
| Linux CUDA and Mac CPU | 0.31.0, unmodified | Qwen3-0.6B (bf16) | Thunderbolt 4 |
| Linux CUDA and Mac Metal (vllm-metal with the transport patch) | 0.30.0, unmodified | Qwen3-0.6B | Thunderbolt 4, both orientations |

Both are two-stage pipeline parallelism (`PP=2`, `TP=1`), through the real vLLM serving engine with the multiprocessing executor and two nodes.

## What was checked

- **Correctness.** Strict deterministic prompts (those whose top-2 log-probability margins are comfortably non-zero) matched single-rank references token for token; 12 concurrent requests were token-identical; request cancellation worked; shutdown was bounded and released GPU memory.
- **Lifecycle.** Repeated process-group create and destroy cycles and repeated engine cycles leaked no file descriptors or threads on the tested versions (a descriptor leak of three per cycle on macOS under vLLM 0.30.0 is vLLM's, not TBCCL's).
- **Integrity.** For the Metal pairing, 2 x 320 transfers (247 MB) between CUDA and Metal had no mismatching element in either rank order.
- **Boundary conversion.** The Metal boundary codecs were checked offline against the reference (argmax agreement 31 of 32 versus 30 of 32 for the baseline; a deliberately wrong codec scored 0 of 32).
- **Failure.** The Metal transport raises structured, bounded errors when a peer exits. The engine is bounded when the leader's own worker dies, and unbounded (vLLM executor semantics) when the headless node's worker dies. Peer-failure tests are loopback only.
- **Link health.** PCIe AER counters were read before and after every physical phase; no fatal or nonfatal error and no interface loss.

## Provenance and gaps

The physical runs of the CUDA and CPU pairing (vLLM 0.31.0) were recorded against an earlier TBCCL wire protocol (3). After the move to wire protocol 4 the unit and loopback suites above were re-run; the physical vLLM runs were **not** repeated. Performance was characterized only, not tuned.

## Known limits

Two-rank groups; `PP=2`, `TP=1`; a single validated model; two boundary codecs (Llama, Qwen3); vLLM 0.30.0 required for the Metal pairing until vllm-metal supports 0.31.0; a dead headless-node worker is not detected by the leader; native vllm-metal MLX-ring pipeline parallelism was not exercised.

## Release-candidate wheel checks

The published 0.2.0rc1 wheels (byte-identical to the release assets) were installed into clean virtual environments on a Linux CUDA host and a Mac, with vLLM 0.30.0 and vllm-metal, and run as a `PP=2`, `TP=1` pipeline over Thunderbolt 4 with the Linux node as node 0: ten engine start and stop cycles, outputs compared with a single-rank CUDA reference (token-identical, prompts up to about 3,500 tokens), with link health unchanged. torch-tbccl was not installed. Engine-level peer death was probed: killing the headless node's process mid-stream leaves the Linux engine stuck (vLLM's executor has no liveness check on a dead headless worker; no TBCCL call is involved), while the same backend through vLLM's pipeline group coordinator fails a lost peer after about one second. A graceful stop of the leader exits in about three seconds and may leave the headless follower waiting in vLLM's ZMQ poll. The CUDA and CPU pairing was not physically repeated with the wheels.

## Not yet done for a release

The final 0.2.0 release itself (no `v0.2.0` tag, wheels or numbered documentation exist yet), a refresh of the vllm-metal patch against the validated vllm-metal revision, and a physical-link rerun of the CUDA and CPU pairing at wire protocol 4 if the release process requires it.
