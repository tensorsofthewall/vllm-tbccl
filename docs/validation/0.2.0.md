## Phase 75C.5 re-validation (vLLM 0.31.0, vllm-metal 0.31.0, TBCCL wire protocol 4)

After the release candidate, the integration was re-validated on the physical Thunderbolt 4 link against the current upstream releases, and a correctness defect found by that work was fixed.

**Stack.** vLLM 0.31.0 (Linux: PyPI wheel with the CUDA 13 build of PyTorch 2.13.0; Mac: vLLM's prebuilt macOS wheel, `0.31.0+cpu`), vllm-metal 0.31.0 (`e7a0c90bec180e5dd4275c473fd7a36e709a930e`) with `vllm-metal-0001-pluggable-pp-transport.patch` (SHA-256 `f0a13f4874dbc7b95973f5e237cdd4b7d02108597dcc707b51cc95ca04c87b07`), MLX 0.32.1, CPython 3.12 on both hosts, Qwen3-0.6B in bf16, `PP=2`, `TP=1`, wheels installed into clean environments (no torch-tbccl). TBCCL 0.6.0 (C ABI 1, wire protocol 4).

| Configuration | Cycles | Result |
|---|---|---|
| CUDA rank 0, Metal rank 1 | 10 engine start/stop cycles | every cycle: the strict prompts and a 28/166/875/2,025/3,507-token sequence token-identical to the single-rank CUDA reference; two rounds of 12 concurrent requests and a cancellation round (8 of 10 streams aborted, then 12 deterministic requests) with no row-mixing divergence |
| Metal rank 0, CUDA rank 1 | 5 engine start/stop cycles | the same gates, no row-mixing divergence |
| CUDA rank 0, CPU (Mac) rank 1 | 10 engine start/stop cycles, wire protocol 4 | the same gates, no divergence |
| Linux CPython 3.13, Mac CPython 3.12 (CUDA rank 0, Metal rank 1) | 2 cycles | the same gates |

**Concurrent-request gate (the row-order fix).** Twelve concurrent requests of 28 to 1,795 tokens, compared token for token with the single-rank CUDA reference. CUDA rank 0 to Metal rank 1: 5 rounds started together 60/60 identical, and 5 rounds with random start jitter 58/60 identical plus 2 numerical ties; Metal rank 0 to CUDA rank 1: 60/60 and 60/60 identical. A "numerical tie" is a first divergence at a position where the reference's top-2 log-probability margin is exactly 0.0 (equal bf16 logits), which flips run to run under different batching; the single-rank CUDA server itself flips at that position in 1 of 96 jittered requests. Across all later campaign cycles no request diverged at a position with a meaningful margin (above 0.05). Before the fix the same test diverged for 6 to 8 of 12 requests on both the 0.2.0rc1 stack and the 0.31.0 stack, with divergence margins of 5 to 10.

**Integrity.** `examples/metal_integrity_probe.py` between the real stages (the CUDA side a vLLM `GroupCoordinator`, the Metal side the real transport), in both rank orders, with the requests' rows ordered differently on the two stages: 2 x 2,560 transfers (989.6 MB each way) with no mismatching element.

**Lifecycle.** Per-process file descriptor and thread counts of the vLLM processes on both hosts were identical before and after load in every cycle of the CUDA/Metal and CUDA/CPU campaigns (the API process on the Mac varies by one Python thread in the Metal-first orientation). After each graceful stop no vLLM process, GPU allocation beyond the idle baseline or listening port remained once the explicitly stopped headless follower had exited; the headless follower lingers after a graceful leader stop (an upstream vLLM behavior, so the harness stops it). vLLM's output handler logs an `EngineDeadError` traceback during shutdown in about one cycle in three; it appears only after the shutdown has begun.

**Link health.** The PCIe AER counters of the Thunderbolt chain were zero before and after every cycle; round-trip time stayed at 0.25 to 0.40 ms.

**Test suites.** Linux (vLLM 0.31.0): 85 passed, 8 skipped on CPython 3.12 and on 3.13. Mac (CPython 3.12, installed wheel, source-free test tree): 93 passed, 6 skipped (the two documentation tests that read the repository are not applicable to a source-free tree). vllm-metal 0.31.0 with the patch: the upstream suite gives the same 44 failures (tests that need model downloads) as a clean checkout, and the seam's own tests pass.

**Defect found and fixed in this phase.** See the [changelog](https://github.com/tensorsofthewall/vllm-tbccl/blob/main/CHANGELOG.md): 0.2.0rc1 derived the CUDA to Metal activation row order from the scheduler output; the real order is the CUDA persistent input batch. The sender now states its actual row order (request ids and row counts, about 450 bytes for 12 requests next to activations of several megabytes) and the receiver computes the permutation; disagreement fails loudly. Unit tests cover identity, reorder, chunked prefill, slot reuse and compaction, and invalid metadata; a Mac integration test uses an input-batch order that differs from the scheduler order; the physical gates above were run in both orientations.

## Release-candidate and earlier validation (historical, vLLM 0.30.0)

The sections below record what was checked for the 0.2.0rc1 release candidate (vLLM 0.30.0 for the Metal pairing, vLLM 0.31.0 for the CPU pairing at TBCCL wire protocol 3). Statements about concurrent requests in them predate the row-order fix above.

## What was checked

- **Correctness.** Strict deterministic prompts (those whose top-2 log-probability margins are comfortably non-zero) matched single-rank references token for token; 12 concurrent requests were run (found later to diverge for CUDA to Metal; see above); request cancellation worked; shutdown was bounded and released GPU memory.
- **Lifecycle.** Repeated process-group create and destroy cycles and repeated engine cycles leaked no file descriptors or threads on the tested versions (a descriptor leak of three per cycle on macOS under vLLM 0.30.0 is vLLM's, not TBCCL's).
- **Integrity.** For the Metal pairing, 2 x 320 transfers (247 MB) between CUDA and Metal had no mismatching element in either rank order.
- **Boundary conversion.** The Metal boundary codecs were checked offline against the reference (argmax agreement 31 of 32 versus 30 of 32 for the baseline; a deliberately wrong codec scored 0 of 32).
- **Failure.** The Metal transport raises structured, bounded errors when a peer exits. The engine is bounded when the leader's own worker dies, and unbounded (vLLM executor semantics) when the headless node's worker dies. Peer-failure tests are loopback only.
- **Link health.** PCIe AER counters were read before and after every physical phase; no fatal or nonfatal error and no interface loss.

## Provenance

The physical runs of the CUDA and CPU pairing for 0.2.0rc1 were recorded against an earlier TBCCL wire protocol (3); they were repeated at wire protocol 4 in the Phase 75C.5 section above. Performance was characterized only, not tuned.

## Known limits

Two-rank groups; `PP=2`, `TP=1`; a single validated model; two boundary codecs (Llama, Qwen3); a dead headless-node worker is not detected by the leader; native vllm-metal MLX-ring pipeline parallelism was not exercised.

## Release-candidate wheel checks

The published 0.2.0rc1 wheels (byte-identical to the release assets) were installed into clean virtual environments on a Linux CUDA host and a Mac, with vLLM 0.30.0 and vllm-metal, and run as a `PP=2`, `TP=1` pipeline over Thunderbolt 4 with the Linux node as node 0: ten engine start and stop cycles, outputs compared with a single-rank CUDA reference (token-identical, prompts up to about 3,500 tokens), with link health unchanged. torch-tbccl was not installed. Engine-level peer death was probed: killing the headless node's process mid-stream leaves the Linux engine stuck (vLLM's executor has no liveness check on a dead headless worker; no TBCCL call is involved), while the same backend through vLLM's pipeline group coordinator fails a lost peer after about one second. A graceful stop of the leader exits in about three seconds and may leave the headless follower waiting in vLLM's ZMQ poll. The CUDA and CPU pairing was not physically repeated with the wheels.
