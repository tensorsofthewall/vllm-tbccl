# vllm-tbccl 0.3.0 validation

```{warning}
**This is not a certification.** vllm-tbccl 0.3.0 is a minor release of 0.2.1 whose wheels bundle TBCCL 0.7.0 (C ABI 1, wire protocol 4). No adapter source changed since 0.2.1; this page records the validation of the development tree and of the CI-built artifacts of release candidate 0.3.0rc1, from which 0.3.0 was promoted without a code change.
```

## What changed

The adapter source is unchanged since 0.2.1. The differences are the TBCCL that the wheels bundle (0.7.0 instead of 0.6.1) and the documentation of the runner requirement.

## Tests on a build against the TBCCL 0.7.0 development tree

| Check | Result |
|---|---|
| Linux adapter test suite (CPython 3.12, vLLM 0.31.0) | 254 passed |
| macOS adapter test suite (CPU environment) | 250 passed |
| Pipeline-boundary benchmark through the real `GroupCoordinator` (`pg_pingpong.py`), 1 to 512 tokens, both orientations | payload verified; round trip about 0.8 ms at 1 token and about 7 ms at 512 tokens |
| Single host, two CUDA ranks, 8 prompts | 8 of 8 token-identical to the single-rank reference |
| Cross-host, Linux CUDA and macOS CPU, 8 prompts, both orientations | 7 of 8 identical in each orientation; the one difference is a near-tie in the next-token probabilities |

## Release-candidate artifacts

The CI-built wheels of 0.3.0rc1 were installed on both hosts, with their checksums, SBOMs and attestations verified, and the loaded `libtbccl` checked to be the 0.7.0 runtime. The wheel test suites ran in CI on the exact commit.

| Check | Result |
|---|---|
| Process-group ping-pong through the vLLM `GroupCoordinator`, 0.2.1 against 0.3.0rc1, interleaved | no consistent regression; payloads verified |
| CUDA and CPU engine, 8 prompts against the single-rank CUDA reference, both orientations | 7 of 8 token-identical in both; the one difference (`water`) is a near tie and is the same as for 0.2.1 |
| CUDA and Metal engine with the pinned vllm-metal fork, project validation client (strict prompts, short, concurrent, cancel phases), both orientations | passed. Over all eight prompts, greedy outputs differed from the CUDA reference in 2 to 3 prompts, all at exact or near ties of the top logits |

Cross-host vLLM requires `VLLM_USE_V2_MODEL_RUNNER=0` on both hosts; the V2 runner is unsupported and a mismatch can stall without an error message.

The physical checks above used a single Linux CUDA / Apple Metal machine pair. PCIe AER reporting was unavailable on the Linux host (`pci=noaer`); no statement about PCIe errors is made.
